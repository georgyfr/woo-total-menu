## 🎯 Objectif de la version

La phase **v1.6.0** a clos la "Phase Polish" : rôles personnalisés, blocs Gutenberg, intégrations Elementor/Bricks/Oxygen et multisite. Restait à apporter deux fonctionnalités majeures attendues par les utilisateurs WooCommerce avancés :

1. **Menus conditionnels** — la possibilité de n'afficher un menu, un header ou un footer que sur certaines pages (boutique, panier, page d'accueil, mobile, période promotionnelle, etc.). Cette fonctionnalité est disponible dans la plupart des page builders premium (Elementor Pro, Bricks Academy, Divi) et constitue une demande forte des e-commerçants qui veulent afficher des menus différents selon le contexte.
2. **Analytics simple** — le module d'analytics était pré-configuré depuis v1.0.0 (settings + capability `wtm_view_analytics`) mais n'avait aucun backend. La v1.7.0 livre un système **privacy-friendly** (aucune donnée personnelle collectée) qui agrège les vues et clics par jour.

La **v1.7.0** livre ces deux modules dans une seule release :

| Fonctionnalité | Statut | Description |
|----------------|--------|-------------|
| `Condition_Evaluator` | Nouveau | Évaluateur runtime de règles de visibilité (10 types de règles, logique AND/OR). |

| `Conditions_Controller` | Nouveau | 4 routes REST `/wtm/v1/menus/{id}/conditions` (GET/PUT/DELETE/test). |
| `Analytics_Controller` | Nouveau | 2 routes REST `/wtm/v1/analytics/track` (public) et `/stats` (admin). |
| Panneau Builder "Conditions" | Nouveau | UI React modale pour éditer les règles + testeur live. |
| Page admin Analytics | Nouveau | Dashboard `/wp-admin/admin.php?page=wtm-analytics` avec chart HTML/CSS. |
| Tracking JS frontend | Nouveau | `sendBeacon` pour les clics, `fetch` pour les vues, déclenché par `data-wtm-menu-id` et `data-wtm-item-id`. |
| Méta `_wtm_conditions` | Nouveau | Stockage JSON des règles, copiée dans les révisions WordPress. |
| `wtm_condition_result` filter | Nouveau | Hook pour étendre l'évaluation (par exemple : règles custom ACF, GEO-IP, etc.). |
| `wtm_analytics_recorded` action | Nouveau | Hook déclenché après chaque événement enregistré. |

## ✨ Nouveautés

### 1. Menus conditionnels — `Condition_Evaluator`

Le nouveau service `WooTotalMenu\Core\Condition_Evaluator` permet d'attacher des **règles de visibilité** à un `wtm_menu`. Ces règles sont évaluées à chaque rendu :

- Côté frontend, le `Location_Interceptor` consulte le `Condition_Evaluator` avant de remplacer un `wp_nav_menu()` par son rendu custom.
- Côté Header/Footer, le `Header_Footer_Injector` consulte le `Condition_Evaluator` avant d'injecter le HTML en `wp_body_open` / `wp_footer`.

Si aucune condition n'est définie, le menu s'affiche toujours (comportement par défaut).

#### 10 types de règles supportés

| Type | Format | Exemples |
|------|--------|----------|
| `page_type` | Enum | `front_page`, `home`, `single`, `page`, `archive`, `search`, `404`, `shop`, `product`, `cart`, `checkout`, `account`, `product_category`, `product_tag` |
| `post_id` | IDs séparés par virgule | `42`, `17, 42` |
| `post_type` | Slug CPT | `post`, `page`, `product` |
| `taxonomy` | `{tax}:{term}` | `category:news`, `product_cat:t-shirts` |
| `user_state` | Enum | `logged_in`, `logged_out` |
| `user_role` | Slug rôle (liste acceptée) | `administrator`, `customer`, `editor` |
| `device` | Enum | `mobile`, `tablet`, `desktop` (détection User-Agent) |
| `date_range` | `{start}..{end}` (dates ISO) | `2026-01-01..2026-12-31` |
| `url_param` | `key=value` ou `key=*` | `utm_source=newsletter`, `promo=*` |
| `language` | Code langue | `en`, `fr` (WPML/Polylang) |

#### Logique de combinaison

- `all` (par défaut) : toutes les règles doivent être vraies (ET logique, court-circuit).
- `any` : au moins une règle doit être vraie (OU logique, court-circuit).

#### Hooks développeur

- `wtm_condition_result` (filter) — permet de surcharger le résultat final.
- `wtm_condition_rule_{type}` (filter) — permet d'ajouter des types de règles custom (par exemple `acf_field`, `geo_country`, etc.).

#### Exemple d'utilisation côté code

```php
$evaluator = new \WooTotalMenu\Core\Condition_Evaluator();
if ( $evaluator->should_render( $menu_id ) ) {
    echo $renderer->render_by_id( $menu_id, 'primary' );
}
```

### 2. Analytics simple — `Analytics`

Le nouveau service `WooTotalMenu\Core\Analytics` stocke des **compteurs journaliers agrégés** pour les événements `view`, `click` et `hover` liés aux menus.

#### Architecture privacy-friendly

Aucune donnée personnelle n'est collectée :

- ❌ Pas d'adresse IP
- ❌ Pas d'user ID
- ❌ Pas de cookie
- ❌ Pas de user-agent
- ✅ Seuls des compteurs agrégés par jour sont stockés
- ✅ Purge automatique après 90 jours (via la méthode `cleanup()`)

#### Stockage

Les compteurs sont stockés dans la table `wp_options` sous forme d'options journalières :

```
wtm_analytics_2026-06-25 → array(
    "42:view:0"     => 17,   // 17 vues du menu #42
    "42:click:12345" => 3,   // 3 clics sur l'item #12345 du menu #42
)
```

Cette approche évite la création d'une table custom et garde le plugin léger, tout en permettant des requêtes rapides (une seule lecture par jour).

#### Tracking JS frontend

Le fichier `assets/front/wtm-frontend.js` écoute :

- Les éléments portant `data-wtm-menu-id` (au chargement) → événement `view` (un seul par menu et par page).
- Les éléments portant `data-wtm-item-id` (au clic) → événement `click` via `navigator.sendBeacon` (pour survivre à la navigation).

Le `Menu_Renderer` ajoute automatiquement `data-wtm-menu-id` au `<nav>` et `data-wtm-item-id` aux `<a>` des items.

#### Configuration

Le panneau **Réglages → Analytics** (auparavant désactivé depuis v1.0.0) est maintenant opérationnel :

- ☑️ Activer la collecte d'analytics (vues et clics sur les menus)
- ☑️ Tracker également les utilisateurs connectés (par défaut, seuls les visiteurs anonymes sont trackés)

#### Page dashboard

Une nouvelle page admin `/wp-admin/admin.php?page=wtm-analytics` affiche :

- 3 cartes KPI : vues totales, clics totaux, CTR (click-through rate).
- Un chart HTML/CSS (pas de dépendance JS) des 7/14/30/90 derniers jours.
- Un tableau "par menu" avec vues, clics et CTR.
- Un filtre par période + par menu.

### 3. REST API — 6 nouvelles routes

#### `/wtm/v1/menus/{id}/conditions` (GET/PUT/DELETE)

- **GET** : retourne les conditions courantes `{ "logic": "all", "rules": [...] }`.
- **PUT** : remplace les conditions (validation automatique).
- **DELETE** : efface toutes les conditions (le menu s'affiche toujours).

#### `/wtm/v1/menus/{id}/conditions/test` (POST)

Évalue les conditions fournies dans le body contre la **requête courante** et retourne un rapport détaillé par règle :

```json
{
  "menu_id": 42,
  "logic": "any",
  "rules": [
    { "type": "user_state", "value": "logged_in", "passed": true },
    { "type": "page_type", "value": "shop", "passed": false }
  ],
  "overall_match": true
}
```

Utile pour prévisualiser le comportement du menu sur la page courante avant de sauvegarder.

#### `/wtm/v1/analytics/track` (POST, public)

Endpoint public (gated par nonce REST) pour soumettre un événement. Le tracking JS l'appelle automatiquement.

```json
{ "menu_id": 42, "event": "view", "item_id": 0 }
```

#### `/wtm/v1/analytics/stats` (GET, admin-only)

Retourne les agrégats filtrables par `start`, `end`, `menu_id`, `event` et `group_by` (`day` | `menu` | `event`).

### 4. Builder React — panneau Conditions

Le Builder React gagne un nouveau bouton dans la barre d'outils supérieure (icône `shield-alt`), qui ouvre une **modale Conditions** :

- Sélecteur de logique (ET / OU).
- Tableau éditable des règles (type + valeur) avec menus déroulants pour les enums (`page_type`, `user_state`, `device`) et inputs libres pour les autres.
- Bouton **Tester sur la page courante** qui appelle l'endpoint `/conditions/test` et affiche un rapport détaillé par règle.
- Bouton **Effacer toutes les conditions** pour réinitialiser.
- Bouton **Enregistrer** qui appelle le `PUT /conditions`.

Le panneau est monté au plus haut niveau de l'arbre React (`App.js`) et ne déclenche pas de re-render du reste du Builder.

---

### 5. Révisions WordPress

La méta `_wtm_conditions` est déclarée comme revision-persisted (via le filtre `_wp_post_revision_meta_keys`) et est restaurée automatiquement quand l'utilisateur restaure une révision depuis le panneau Historique. Le `Meta_Boxes::restore_revision_meta()` gère également cette nouvelle clé.

## 🛡️ Confidentialité

Le module Analytics a été conçu **dès le départ** pour ne pas nécessiter de bannière de consentement RGPD :

- Aucune donnée personnelle n'est collectée (ni IP, ni user-agent, ni identifiant).
- Les événements sont agrégés en compteurs journaliers.
- Les données sont automatiquement purgées après 90 jours.
- Le tracking peut être désactivé globalement dans Réglages → Analytics.
- Les utilisateurs connectés sont exclus par défaut (réglable).

Cette approche est conforme au RGPD européen et au CCPA californien.

## 📦 Migration & compatibilité

- Aucune migration DB nécessaire — la nouvelle méta `_wtm_conditions` est créée à la volée.
