# Version 1.7.1 — Détection des menus WordPress natifs

**Date de sortie** : 2026-06-26
**Tag Git** : [`v1.7.1`](https://github.com/georgyfr/woo-total-menu/releases/tag/v1.7.1)
**ZIP** : <https://github.com/georgyfr/woo-total-menu/releases/download/v1.7.1/woo-total-menu-1.7.1.zip>

## 🎯 Objectif de la version

Correctif de régression fonctionnelle : les menus WordPress natifs (ceux créés via `Apparence → Menus`, `/wp-admin/nav-menus.php`) n'étaient **pas détectés** par le plugin.

Le module `menu` du Header/Footer Builder n'acceptait qu'un `post_id` de `wtm_menu` saisi manuellement, sans proposer de liste déroulante ni prendre en charge les `nav_menu` natifs de WordPress.

Cette version 1.7.1 introduit :

1. Un **dropdown unifié** dans le Builder qui liste à la fois les `wtm_menu` posts et les `nav_menu` natifs.
2. Une nouvelle route REST `GET /wtm/v1/wp-menus` exposant la liste des menus natifs.
3. La délégation du rendu vers `wp_nav_menu()` lorsque la source est `"wp"`.

## ✨ Nouveautés

### 1. Dropdown unifié dans le module `menu`

Le panneau de propriétés du module `menu` (Header/Footer Builder) expose désormais un `<select>` groupant les menus disponibles en deux `<optgroup>` :

- **Menus Woo Total Menu** : `wtm_menu` posts (post_id, titre, statut).
- **Menus WordPress natifs** : `nav_menu` terms (term_id, nom, count).

La sélection est décomposée en deux settings :

```json
{
  "menu_source": "wp",   // "wtm" (défaut) ou "wp"
  "menu_id":     18      // post_id si "wtm", term_id si "wp"
}
```

#### Comportement rétro-compatible

Les modules `menu` existants sans `menu_source` continuent de fonctionner comme avant : la valeur par défaut `"wtm"` est appliquée silencieusement, et le `menu_id` est interprété comme un `wtm_menu` post ID.

### 2. Route REST `GET /wtm/v1/wp-menus`

Nouveau contrôleur `WP_Menus_Controller` (`src/Api/WP_Menus_Controller.php`) exposant :

```http
GET /wp-json/wtm/v1/wp-menus
Authorization: X-WP-Nonce (capability: wtm_manage_menus)
```

Réponse :

```json
{
  "menus": [
    {
      "id": 18,
      "name": "Menu WP Test 29",
      "slug": "menu-wp-test-29",
      "count": 2,
      "locations": [],
      "edit_url": "http://example.com/wp-admin/nav-menus.php?menu=18"
    }
  ],
  "locations": {
    "wtm_primary": "[WTM] Menu principal (header)",
    "wtm_footer": "[WTM] Pied de page",
    "wtm_sidebar": "[WTM] Barre latérale",
    "wtm_mobile": "[WTM] Menu mobile dédié"
  }
}
```

### 3. Rendu frontend — `render_wp_nav_menu()`

Nouvelle méthode privée `Header_Footer_Renderer::render_wp_nav_menu()` qui :

- Vérifie l'existence du `nav_menu` term via `get_term($term_id, 'nav_menu')`.
- Appelle `wp_nav_menu()` avec un wrapper `<nav class="wtm-nav wtm-wp-nav">` cohérent avec le reste du plugin.
- Retourne une chaîne vide si le menu n'existe pas (pas d'erreur fatale).

#### Hooks développeur

- `wtm_wp_nav_menu_args` (filter) — surcharge les arguments `wp_nav_menu()`.
- `wtm_wp_nav_menu_html` (filter) — filtre le HTML rendu final.

### 4. Prévisualisation différenciée

L'iframe de prévisualisation affiche désormais `[Menu WP #N]` ou `[Menu WTM #N]` selon la source, pour distinguer visuellement les deux types dans le Builder.

## 🔧 Hooks développeur

### Filtres

- `wtm_wp_nav_menu_args` (array $args, WP_Term $term, string $location) — surcharge les arguments `wp_nav_menu()` utilisés pour rendre un menu WP natif dans un module `menu`.
- `wtm_wp_nav_menu_html` (string $html, WP_Term $term) — filtre le HTML rendu final d'un menu WP natif.

### Exemple

```php
// Forcer une profondeur maximale de 2 pour les menus WP natifs
add_filter( 'wtm_wp_nav_menu_args', function( $args, $term, $location ) {
    $args['depth'] = 2;
    return $args;
}, 10, 3 );
```

## 📦 Migration & compatibilité

- **Aucune migration DB nécessaire** — la nouvelle clé `menu_source` est créée à la volée dans les settings du module.
- **100 % rétro-compatible** : un `wtm_menu` existant avec un header/footer config qui utilise un module `menu` sans `menu_source` continue de fonctionner comme avant (défaut = `"wtm"`).
- La nouvelle route REST est enregistrée sur `init`, donc accessible immédiatement après activation.

## 🧪 Tests effectués

- **Lint PHP** : 4 fichiers modifiés (tous passent `php -l`).
- **Activation plugin** : WP-CLI plugin activate OK.
- **Endpoint REST** : `GET /wtm/v1/wp-menus` retourne la liste des `nav_menu` natifs avec leurs `term_id`, `name`, `slug`, `count`, `locations` et `edit_url`.
- **Rendu backend** : `render_module_menu()` avec `menu_source=wp` + `menu_id=18` retourne le HTML `<nav class="wtm-nav wtm-wp-nav">…</nav>` contenant les items du menu natif.

- **Edge case** : `render_module_menu()` avec `menu_source=wp` + `menu_id=99999` (menu inexistant) retourne une chaîne vide (pas d'erreur fatale).
- **Sauvegarde REST** : `PUT /wtm/v1/menus/11` avec un `header_config` contenant un module `menu` source `"wp"` persiste correctement et est retourné intact par `GET /wtm/v1/menus/11`.
- **Build webpack** : `npm run build` compile sans erreur, le bundle contient le nouveau code `MenuModuleEditor` et `useAvailableMenus`.
