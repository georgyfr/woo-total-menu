# Version 1.1.5 — Historique des révisions WordPress + restauration

- **Date de sortie** : 2026-06-25
- **Statut** : ✅ Livrée
- **Tag Git** : [`v1.1.5`](https://github.com/georgyfr/woo-total-menu/releases/tag/v1.1.5)
- **ZIP de release** : [woo-total-menu-1.1.5.zip](https://github.com/georgyfr/woo-total-menu/releases/download/v1.1.5/woo-total-menu-1.1.5.zip)

## 🎯 Objectif de la version

Cette version ajoute la **gestion historique des révisions WordPress** au
Builder. Concrètement, chaque sauvegarde crée désormais une révision du CPT
`wtm_menu`, capturant à la fois les champs du post (titre, statut) ET les 6
métadonnées WTM (`_wtm_config`, `_wtm_menu_type`, `_wtm_location`,
`_wtm_header_config`, `_wtm_footer_config`, `_wtm_version`).

L'utilisateur peut :

- ✅ **Lister** les révisions passées dans un nouveau modal « Historique »
  accessible depuis le header du Builder
- ✅ **Prévisualiser** une révision dans l'iframe de preview sans toucher à
  l'état live du menu (un pill jaune « Révision #N » s'affiche)
- ✅ **Restaurer** une révision — flow avec confirmation inline, l'état
  local est remplacé par la version restaurée, l'undo/redo local est vidé

Cette version s'aligne sur les spec §6.6 (Undo/Redo et historique), §7.6
(Révisions et historique) et §9.9 (Annulation / Rétablissement).

## 🚀 Nouveautés (Added)

### 1. Controller REST `Revisions_Controller`

**Fichier** : `src/Api/Revisions_Controller.php` (nouveau, ~410 lignes)

Trois routes REST exposées sous `/wtm/v1/menus/{id}/revisions` :

| Méthode | Route | Description |
|---------|-------|-------------|
| `GET`  | `/menus/{id}/revisions` | Liste paginée des révisions. Chaque item contient l'auteur (ID, display_name, avatar), la date (ISO 8601 + relative), le nombre d'items (comptage récursif), et le snapshot complet du config décodé en JSON. Headers `X-WP-Total` et `X-WP-TotalPages`. |
| `GET`  | `/menus/{id}/revisions/{revision_id}` | Récupère une révision spécifique avec son snapshot. |
| `POST` | `/menus/{id}/revisions/{revision_id}/restore` | Restaure la révision : appelle `wp_restore_post_revision()` (post fields only), puis copie manuellement les 6 meta WTM depuis la révision vers le post parent. Retourne le menu restauré au format `Menu_Controller::format_item()`. |

**Sécurité** :
- `permission_callback` = `current_user_can('wtm_manage_menus')` sur toutes
  les routes
- Vérification que la révision appartient bien au menu parent
  (`post_parent === $post_id`) avant toute restauration

### 2. Filtre `wtm_max_revisions` (spec §7.6)

**Fichier** : `src/Core/CPT_Manager.php` (+30 lignes)

Nouveau hook `wp_revisions_to_keep` qui applique le filtre
`wtm_max_revisions` (défaut 10) sur le CPT `wtm_menu`. Un administrateur
peut l'ajuster via un `add_filter()` classique :

```php
// Garder 25 révisions au lieu de 10
add_filter( 'wtm_max_revisions', function () { return 25; } );
```

### 3. Métadonnées WTM versionnées dans les révisions

**Fichier** : `src/Admin/Meta_Boxes.php`

Les 6 meta WTM sont désormais enregistrées avec `revisions_enabled => true`
(paramètre ajouté dans WP 6.4 à `register_post_meta()`). Pour la
compatibilité ascendante (et pour suivre la doc WP qui recommande les deux
mécanismes), le filtre `_wp_post_revision_meta_keys` est également hooké
pour déclarer explicitement les 6 clés comme revision-persisted.

Deux nouveaux hooks dans le constructor :

- `_wp_post_revision_meta_keys` → `register_revision_meta_keys()`
- `wp_restore_post_revision` → `restore_revision_meta()`

Le second garantit que lorsqu'une révision est restaurée via WP core (par
exemple depuis `/wp-admin/revision.php`), les meta WTM sont elles aussi
restaurées — pas seulement les post fields.

### 4. Composant React `HistoryPanel`

**Fichier** : `builder/components/HistoryPanel.js` (nouveau, ~210 lignes)

Modal centré avec overlay :

- **Ouverture** : bouton « Historique » (icône `dashicons-backup`) dans le
  header du Builder, à côté des boutons Undo/Redo. Désactivé pour les
  nouveaux menus non sauvegardés (`!menu?.id`).
- **Fermeture** : Escape, clic sur le backdrop, ou bouton Close.
- **Liste** : chaque ligne affiche l'avatar Gravatar (32px) de l'auteur,
  son nom, la date relative (« il y a 5 min »), le nombre d'items de la
  révision, et un bouton « Restaurer ».
- **Prévisualisation** : cliquer une ligne envoie la config de la révision
  à l'iframe de preview via `postMessage`, sans modifier l'état live du
  menu. Un pill jaune « Révision #N » s'affiche dans le header du panneau
  de preview. Recliquer la ligne revient à la config live.
- **Restauration** : bouton « Restaurer » → bannière de confirmation
  inline jaune « Restaurer cette révision ? » avec boutons Confirmer /
  Annuler → appel `POST .../restore` → le menu est remplacé →
  `clearHistory()` pour vider les piles undo/redo locales → fermeture du
  modal après 600 ms.
- **Annonces ARIA** : chaque action (ouverture, prévisualisation,
  restauration) émet un message `aria-live="polite"` en français.

### 5. Store `wtm/menu` étendu

**Fichier** : `builder/stores/menu.js`

Nouvel état :
```js
revisions: [],
isLoadingRevisions: false,
isRestoring: false,
```

Nouvelles actions :
- `setRevisions(revisions)` — remplace la liste
- `setIsLoadingRevisions(bool)` — flag de chargement
- `setIsRestoring(bool)` — flag de restauration
- `loadRevisions(menuId)` — async thunk qui appelle
  `GET /wtm/v1/menus/{id}/revisions?per_page=50`
- `restoreRevision(menuId, revisionId)` — async thunk qui appelle
  `POST /wtm/v1/menus/{id}/revisions/{rev_id}/restore`, met à jour le
  menu, vide l'historique local, et recharge la liste des révisions

Nouveaux sélecteurs : `getRevisions`, `isLoadingRevisions`, `isRestoring`.

### 6. Store `wtm/ui` étendu

**Fichier** : `builder/stores/ui.js`

Nouvel état :
```js
isHistoryOpen: false,
previewRevisionId: null,  // null = live config, number = previewing revision
```

Nouvelles actions : `openHistory()`, `closeHistory()`,
`setPreviewRevision(revisionId)`.

Nouveaux sélecteurs : `isHistoryOpen`, `getPreviewRevisionId`.

### 7. PreviewPanel étendu

**Fichier** : `builder/components/PreviewPanel.js`

Calcule désormais `effectiveConfig` = config de la révision prévisualisée
OU config live du menu. Cette `effectiveConfig` est envoyée à l'iframe
via `postMessage` avec le debounce 250 ms habituel. Un pill jaune
« Révision #N » s'affiche dans le header du panneau de preview quand une
révision est en cours de prévisualisation.

## 🔧 Modifications (Changed)

### 1. `Menu_Controller::update_menu()` — garantir une révision à chaque save

**Fichier** : `src/Api/Menu_Controller.php`

WordPress ne crée une révision que si un *post field* change (titre,
content, excerpt, etc.). Les modifications meta-only n'en créaient aucune,
ce qui aurait rendu l'historique inutilisable dans le Builder (où la
plupart des saves ne changent que `_wtm_config`).

Solution : on écrit désormais une signature dérivée du config dans le champ
`post_content` à chaque save :

```php
$update_args['post_content'] = 'wtm:' . substr( md5( $signature ), 0, 16 ) . ':' . time();
```

Le champ `time()` garantit l'unicité entre deux saves consécutifs même si
le config n'a pas changé — ce qui permet de forcer la création d'une
révision sur clic explicite « Enregistrer ».

### 2. Header.js — bouton Historique

**Fichier** : `builder/components/Header.js`

Un 3e bouton « Historique » (icône `dashicons-backup`) est ajouté dans le
group undo/redo, à droite des boutons Undo et Redo. Il est désactivé pour
les nouveaux menus non sauvegardés (`!menu?.id`) ou pendant le chargement.
Cliquer déclenche `loadRevisions(menu.id)` puis `openHistory()`.

### 3. Bump Requires at least 6.3 → 6.4

Le paramètre `revisions_enabled` de `register_post_meta()` a été ajouté
dans WordPress 6.4. La spec §7.6 mentionne d'ailleurs explicitement
WP 6.4 (« Depuis WP 6.4, les méta sont incluses dans les révisions pour
les CPT qui les supportent »). Le `Requires at least` passe donc de 6.3
à 6.4 dans `readme.txt` et `woo-total-menu.php`.

### 4. CSS — ~230 lignes ajoutées

**Fichier** : `builder/style.css`

Styles pour :
- L'overlay et le modal (`wtm-history-modal__*`)
- Les items de la liste (`wtm-history-item*`) avec état `is-previewing`
- Les boutons génériques `wtm-btn`, `wtm-btn--sm`, `wtm-btn--secondary`,
  `wtm-btn--danger`
- Le pill de prévisualisation de révision dans le panneau de preview
  (`wtm-preview__revision-pill`)
- Animations `wtm-history-fadein` et `wtm-history-slide` (180 ms et 220 ms)
- Animation `wtm-spin` pour les loaders

## 🔐 Sécurité

- Toutes les routes `revisions/*` requièrent la capacité
  `wtm_manage_menus` via `permission_callback`.
- `restore_revision` vérifie que la révision appartient bien au menu
  parent (`post_parent === $post_id`) avant toute restauration.
- Le hook `wp_restore_post_revision` ne restaure les meta WTM que si le
  post parent est bien de type `wtm_menu` (pas de fuite vers d'autres
  CPT).
- Le modal utilise `role="dialog"` + `aria-modal="true"` pour
  l'accessibilité.
